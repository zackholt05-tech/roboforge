# 1. PROJECT OBJECTIVE, SCOPE, AND PRODUCT STORY

## 1.1 Central scientific question

**Can a conditional diffusion action-sequence policy match or outperform deterministic and recurrent behavior-cloning policies on closed-loop three-dimensional robotic manipulation, particularly under variation in object placement and initial robot state?**

Investigate *why* each model succeeds/fails, whether action multimodality matters, and how observation/action horizons and guidance/sampling settings influence performance and latency. This is an empirical research question, **not** a promise that diffusion will win.

## 1.2 The two research levels — order is mandatory

**LEVEL 1 — REQUIRED CORE: 3D robot manipulation.** Train policies using a fixed, verified set of low-dimensional simulator observations (robot proprioception and, if the dataset provides it, object/goal state). These features control a **real 3D articulated robot**, but may encode privileged simulator information rather than perception. Reach robust repeated-seed results for a primary task and a secondary task. Add a controlled RGB+proprioception experiment when technically and economically feasible, with separate results and clearly stated observation differences. **Do not delay a valid state-based Level 1 paper to chase point clouds.**

**LEVEL 2 — ADVANCED, SEPARATELY GATED: explicit 3D perception.** After Level 1's final benchmark is frozen, build a camera-calibrated RGB-D/point-cloud pipeline from consistent simulator state. Train a compact point-cloud-conditioned diffusion policy (DP3-inspired, not automatically an exact reproduction), compare it with a matching RGB baseline under identical observations/training/evaluation states, and study spatial generalization. Level 2 must be marked **experimental/optional** if dataset reconstruction, sensors, licenses, or budget do not pass the feasibility gate. Failure to finish Level 2 must **not** invalidate a completed Level 1 research release.

## 1.3 Tasks, prioritized and accurately named

| Priority | Environment/dataset | Real task | Role | Requirement |
|---|---|---|---|---|
| P0 | `Lift` (robosuite / robomimic PH) | Articulated robot grasps and lifts a cube | Primary controlled benchmark | **Mandatory** |
| P1 | `Can` (robosuite / robomimic PH) | Grasp and place a can into a designated bin | Transfer of benchmark method to harder placement | **Mandatory if feasibility gate passes; otherwise explicitly scoped core result + blocked extension** |
| P2 | `Square` (PH), or compatible `StackCube` from **ManiSkill** only as an explicitly separate dataset/framework | Precision insertion or stacking, respectively | Stretch difficulty | Optional; do not call Square “Stack” |
| P3 | RGB-based policy for `Lift`, then `Can` if feasible | Same physics tasks with camera observations | Level 1 visual-policy extension | Conditional on observation extraction proof + budget |
| P4 | Depth/point clouds for a matched manipulation task | Explicit geometry-aware control | Level 2 | Advanced optional gate |

**Do not silently mix robomimic/robosuite datasets with ManiSkill physics, controllers, rewards, or action conventions.** ManiSkill is a fallback **only if the primary stack fails Session 0**, and replacing the stack requires a recorded owner-approved revision of the protocol, with separately validated replay and evaluation. If `Can` cannot be obtained in a compatible version, do not invent a pick-and-place dataset or pass off `Lift` as `Can`.

## 1.4 Minimum finished product

A defensible public RoboForge release includes: (a) reproducible data ingestion and simulation; (b) ≥2 learned baselines and an actual trained conditional diffusion policy; (c) repeated-seed closed-loop comparisons on Lift, with a second task if verified; (d) paired held-out evaluation and transparent CIs/failures; (e) budget-guarded remote GPU training and checkpointing; (f) at least one authentic full-3D interactive rollout viewer, with verified kinematic fidelity; (g) real denoising-stage visualizations; (h) paper-style research report; (i) clean CI, documentation, and downloadable or reproducible visual samples; (j) correct sole project authorship and scientific attribution.

**No implication of physical-robot deployment.** This project is entirely simulated. Distinguish *3D physics simulation* from real hardware and distinguish *state conditioning* from the ability to infer arbitrary 3D geometry from pixels.

## 1.5 Explicit exclusions

Not a general-purpose robotics foundation model, not language-conditioned robot control, not multi-robot planning, not real-world autonomous actuation, not reinforcement learning from scratch, not an LLM wrapper, not a full simulator built in WebGL, and not an unsupervised robotics benchmark. Do not add authentication, payments, databases, model serving endpoints, or agent dashboards to the showcase unless essential and approved. A static hosted site based on compressed verified artifacts is preferable to a live inference backend.

# 3. RESEARCH DESIGN: HYPOTHESES, FAIRNESS, AND PRECOMMITMENT

## 3.1 Prespecified hypotheses (do not assume true)

- **H1 — closed-loop competence:** Trained diffusion and BC policies improve true success over a non-learned random-action sanity baseline.
- **H2 — method comparison:** Diffusion's closed-loop success may exceed deterministic BC on task distributions with multiple valid action sequences. Compare using paired initial states and uncertainty intervals; explicitly allow a null or negative finding.
- **H3 — temporal conditioning:** A recurrent policy and a diffusion policy with observation history may outperform one-frame deterministic BC; measure costs and separate *history benefit* from *generative architecture benefit*.
- **H4 — robustness:** Policies may differ in sensitivity to object placement, robot initial condition and visuomotor perturbation. Robustness claims apply only to perturbations implemented and actually tested.
- **H5 — optional point-cloud extension:** With identical episodes and held-out initial states, explicit 3D perception may improve positional generalization compared with RGB-conditioned policies; not assumed, and only meaningful with a matched visual-data protocol.

**Avoid an apples-to-oranges study.** Establish core comparisons on the exact same state observation set and action control. Label RGB and point-cloud results by modality, data, and compute budget. Never claim RGB or point-cloud policies beat a privileged-state policy in a “fair perception comparison” without acknowledging the extra state privilege.

## 3.2 Experimental hierarchy and freeze rules

1. **Engineering controls:** check random action, demonstration replay, short-horizon overfit on a few demonstrations, validation curves, reward/success consistency. These are *not* research performance claims.
2. **Level 1 core development:** select models/settings using training and validation data + validation rollout starts only. Make one canonical primary protocol per task, with actual success-based checkpoint selection where feasible.
3. **Level 1 final held-out test:** only after writing and committing `docs/FINAL_TEST_FREEZE.md` with dataset IDs, algorithm configurations, model selection rule, fixed test initial-state schedule, metrics, comparisons and analysis plan. Run the entire locked protocol once per designated checkpoint (repeated stochastic model rollouts allowed if prescribed). Any revisit of the test is labelled exploratory or separate replication; do not silently tune to the test.
4. **Level 1 robustness:** evaluate independent, explicitly defined perturbation sets. Use a distinct validation regime for selecting perturbation magnitude if needed; freeze ranges before main robustness results.
5. **Level 1 RGB extension:** run as an explicitly segregated observation-modality study, not a revision of core test numbers.
6. **Level 2 point-cloud:** requires its own preregistration, budget sign-off, and frozen test schedule. Never relabel an early unsuccessful point-cloud experiment as a successful “3D perception” result.

## 3.3 Dataset splitting and leakage prevention

- For each task, deterministically hash whole episode IDs (and, if available, operator identity) to train/validation/optional held-out demonstration subsets, with a seed locked in config; document all IDs. A typical exploratory division might be 80/10/10 **if episode count and dataset conventions justify it**; do not imply this is the original robomimic benchmark's required split.
- Train and validation windows must never cross their episode boundary. Construct past observation histories and future action targets within one trajectory; define boundary behavior (repeat edge observation versus drop window), and mask padding from losses.
- Fit state/action normalization on training episodes only and save reversible transforms. Use the exact transform at inference and correct action clipping for the simulator's actual action space.
- If provided human dataset includes demonstrator identities, report the distinction between within-demonstrator and held-out-demonstrator claims; don't invent operator metadata.
- Rollout evaluation seeds and initial states are not equivalent to the demonstration split: define and freeze both separately. Never evaluate the policy by replaying ground-truth demonstration actions and count that as autonomous success.
- Keep training dataset and derived RGB/depth/point-cloud representations aligned via immutable `task`, `episode_id`, `step_index`, original state/hash and camera metadata. Do not produce inconsistent labels by resimulating with different control physics.

## 3.4 Minimum statistically meaningful evaluation

**Target default when compute permits:** For each task, train **3 independent model seeds per primary algorithm**, and evaluate each seed on the **same 50 held-out initial-state seeds**, for 150 policy-seed × initial-state trials per model/task. The agent must benchmark rollout cost and request a smaller precommitted plan if that is unaffordable; do not claim statistical power merely because 50 starts were used. Use more repeats when uncertainty is large and cost permits, but do not add only favorable ones.

Metrics:

- **Primary:** fraction of episodes achieving the simulator's task success criterion before the defined horizon; report numerator/denominator, confidence interval, model-seed spread, and paired difference against baseline.
- **Secondary:** steps to first success, success persistence if relevant, normalized task-progress/goal-distance only if the task defines it legitimately, collision/contact failure categories when observable, trajectory/path length, action smoothness/jerk (with time-step units), action saturation, control frequency, inference-time latency, training-time GPU-hours, and approximate actual dollars.
- **Diffusion-specific:** samples per decision, denoising iterations, plan diversity under repeated stochastic samples, execution horizon, rejection/clipping frequency; record actual noise/denoising tensors and conditional state.
- **Uncertainty:** bootstrap by **held-out initial state** with policy training seed treated as a separate variation source (e.g., hierarchical bootstrap or per-seed summaries plus paired state bootstrap). Use fixed bootstrap seed and disclose method. Do not treat multiple time steps from one rollout as independent observations.
- For deterministic models, multiple repeated evaluations on identical initial conditions might be duplicates. Do not increase apparent sample size by rerunning identical trajectories. For diffusion stochasticity, prescribe policy noise seeds independently and document the sampling unit.
- Always show per-task and per-model denominators, all failed or timed-out trials, any NaNs, exception counts, and early simulator resets.

**Mandatory truthfulness:** Don't use statistical significance alone to establish “better”. Report absolute changes, uncertainty, practical relevance, speed/cost tradeoffs, and constraints on interpretation. Do not report benchmark-paper results as your own.

## 3.5 Evaluation starts, domain shift, and distributions

- Create a versioned `eval_states.jsonl` or equivalent with stable initial simulator configuration and state identifiers. Reset from the same conditions for all models, avoiding unintended different randomization sequences.
- Verify that two fresh simulator processes reloading one specified state produce compatible robot/object configurations and near-identical short deterministic rollouts under identical controls. Record maximum discrepancies.
- Define **in-distribution** starts from the benchmark's standard reset distribution and **out-of-distribution** variants with explicit bounds (e.g., object initial XYZ position shifts, yaw differences, gripper start pose shifts), **only if physically realizable** and replayable. Avoid unsupported camera changes that invalidate observation labels.
- Do not claim spatial OOD if only the random seed changed within the normal training distribution. Keep appearance/camera OOD separate from geometric OOD.
- Define a small hand-audited set of demonstration failures and successful rollouts selected by **predefined selection criteria** for visuals, not “the nicest-looking” training clip.

# 4. SIMULATION, DATA, AND POLICY INTERFACES

## 4.1 Canonical environment wrapper contract

Create `RoboForgeEnv` with a typed, documented adapter over the selected pinned simulator. It must provide methods analogous to:

```python
reset(initial_state_or_seed) -> Observation, EpisodeMetadata
step(action: np.ndarray) -> Observation, reward, terminated, truncated, info
serialize_initial_state() -> Mapping
get_robot_kinematics() -> JointStateAndTransforms

```

The exact underlying robosuite API may differ. Build adapters, **not** modifications of site-packages. Use a state snapshot that includes all needed model XML, episode metadata, MuJoCo generalized positions/velocities, mocap state/actuator state when needed, control setup and task randomization to achieve deterministic resets. Never rely on a global random seed alone if the simulator samples hidden state.

Expose semantic constants from **actual metadata**: robot name, joint names, link hierarchy, gripper actuator name, control frequency `Hz`, action min/max and dimension, control mode, camera names/intrinsics/extrinsics, task success function, observation keys, and privileged features. Test shape contracts at every layer.

## 4.2 Observation dictionary and modality contracts

Use explicit names rather than concatenating undocumented arrays:

```text
observation:
  robot:
    joint_pos          # shape: [n_joints] from active robot
    joint_vel          # if provided and permitted
    end_effector_pose  # 3D position + documented rotation encoding
    gripper_state      # actual simulator-provided dimensionality
  object_state:         # only for state-based Level 1; privileged if exact simulator pose
    position / orientation / target_state / optional contacts
  rgb:                  # optional Level 1 image policy
    camera_id -> uint8 [H,W,3]
  depth:                # Level 2 only
    camera_id -> calibrated metric or documented depth units
  point_cloud:          # Level 2 only
    xyz [N,3], optional rgb/segmentation, valid mask, coordinate frame
```

Any added key must be declared in `ObservationSpec` and in a run manifest. **RGB-only** means robot proprioception + camera image, but no object ground-truth pose; do not accidentally leak `object_state` through normalization, timestep metadata, labels, or model input plumbing. Goal specification may be available if objectively part of the policy's task definition; document it.

For each algorithm, log the exact input tensor shapes, dynamic ranges, mask/padding, history ordering, and frame transformations. Test that batches are finite and have no mismatched frame/action alignment.

## 4.3 Action conventions, horizons, and control loop

Actions may involve end-effector Cartesian deltas, orientation commands, joint controls, and gripper control. **Do not assert a fixed 7D vector** without dataset validation. For a system with 3 positional, 3 rotational, and 1 gripper command, 7D might be appropriate, but the actual controller can differ.

Use a single canonical action representation per benchmark. Write reversible mappings:

- `dataset_action -> normalized_model_action` for loss and diffusion sampling;
- `normalized_model_action -> clipped_env_action` for simulator step;
- optional `env_action -> readable_world_motion` for visualization, never infer Cartesian motion simply by plotting raw joint commands.

Target default **observation horizon** `T_o=2`, **prediction horizon** `T_p=16`, **execution horizon** `T_a=8`, consistent with common Diffusion Policy configurations, but **verify each number** against demonstration length, controller rate, robot response and memory budget. Freeze selected values on validation; do not optimize them on test outcomes. The action chunk is recomputed in receding-horizon fashion after executing `T_a` actions; never play the entire predicted plan forever without sensing again.

Guard against: wrong axis order, reward misalignment, off-by-one action targets, action-limit violation, gripper sign inversion, quaternion antipodes, angle discontinuities, inconsistent frame definitions, and inconsistent task-specific action spaces.

## 4.4 Dataset schema and run provenance

Store third-party HDF5 datasets under ignored `data/raw/`. # 5. LEARNING SYSTEM — REQUIRED MODELS, LOSSES, AND CONTROLS

## 5.1 Shared training and inference framework

Build a common `Policy` interface with methods `train_batch`, `act`, `reset_episode`, `save_checkpoint`, `load_checkpoint`, and `export_diagnostics`. Keep common observation preprocessing, normalizers, action bounds, episode buffering, checkpoint/manifest code, metrics and evaluator across algorithms. All models must accept `ObservationSpec` and `ActionSpec`, never hard-code PushT dimensions.

Log losses on train/validation, optimizer settings, gradient norms, seeds, parameter counts, training samples/steps, effective batch sizes, inference latency, and model selection. Checkpoints include full model/optimizer/scheduler state, normalization stats, config, dataset/split hash, global step, RNG states if practical, code revision and training device. Test strict reload, resume and forward equivalence. No checkpoints committed to Git unless size/license and approval make sense; provide reproducible download instructions and SHA-256.

Train 1 tiny batch locally on CPU first to verify the pipeline. Perform short deliberate overfit of 1–4 demonstration episodes to demonstrate that training can learn. This is a **unit/integration sanity test**, not published benchmark success.

## 5.2 Baseline A: deterministic behavior cloning (mandatory)

- **State Level 1:** MLP with 2–4 residual or standard blocks, layer norm as useful, configurable width (e.g., 256), projecting current/short-history state to normalized action.
- Support an optional lightweight RGB encoder for the image-extension study, with *identical image backbone across compared policy families when practical*.
- Train with masked action MSE or Huber; choose based on validation, report what each dimension means. Optionally predict an action **chunk**, not only one step, if matching diffusion action horizon is crucial. Include a strictly matched one-step ablation if testing chunking.
- Measure actual closed-loop success. Include no-op/random sanity baselines for completeness, but do not make them primary learned comparators.

## 5.3 Baseline B: recurrent behavior cloning (mandatory)

- GRU/LSTM over observation histories, with hidden-state reset at episode boundary and careful handling of truncation/padding.
- Predict current action or action chunk with declared setup and a comparison controlling for output horizon.
- Match training data and approximate parameter count as feasible; report if capacities differ materially.
- Explicitly test that rolling observations influence results and hidden state does not carry between evaluation episodes.

## 5.4 Baseline C: stochastic mixture policy (optional but desirable)

- Gaussian mixture policy (mixture-density network) or robomimic's compatible GMM-BC variant; parameterize K component means, scales and weights.
- Use correct negative log likelihood and bounded/executed actions; avoid training loss exploding from invalid scales.
- This helps isolate whether diffusion's advantages reflect **stochastic action modeling** or other architecture features. Include only if budget permits a statistically credible comparison, not as a half-trained table filler.

## 5.5 Main algorithm: conditional diffusion action policy (mandatory)

Implement or carefully adapt a **conditional denoising diffusion model for continuous action sequences**. The recommended starting architecture is a **1D temporal U-Net**, conditioning on history of robot/object observations (and later RGB features). Incorporate scheduler and model components with tested, documented semantics, referring to the official Diffusion Policy and robomimic 0.5 reference implementation.

Minimum training sequence:

1. Encode `T_o` permitted observations into a conditioning representation `c`.
2. Take normalized target action sequence `A_0 ∈ R^{T_p × action_dim}`.
3. Sample diffusion time `t` and Gaussian noise `ε`; form `A_t = sqrt(ᾱ_t) A_0 + sqrt(1−ᾱ_t) ε` for an appropriate DDPM-style schedule.
4. Predict `ε̂ = f_θ(A_t, t, c)` (or a documented alternative target such as `v`) using a masked loss, recording the exact prediction target in the config.
5. At inference sample a noisy action chunk with the declared noise schedule, denoise for specified inference steps, invert normalization, clamp to action constraints and execute only the next `T_a` commands before replanning.

A network outputting a single deterministic action after one forward pass **is not a diffusion policy**. Test the noise-scheduler equations, timestep embedding, reverse denoising shapes, condition leakage, EMA model behavior if used, temporal padding masks, observed-state consistency, dynamic action ranges and deterministic seeded sampling.

**Validation reference:** Compare shapes and a synthetic training case against robomimic's official Diffusion Policy template; where adapted rather than independently implemented, mark which components came from external packages and license them. Do not present a wrapper around off-the-shelf scripts as a new diffusion algorithm. The original contribution can be a rigorous controlled benchmark and authentic observatory rather than inventing a new diffusion sampler.

Suggested initial hyperparameter search *bounds, not sacred values*: U-Net width `64–256`, 2–3 down/up stages, schedule `DDPM/DDIM`, 10–100 inference denoising steps, history 1–3, prediction horizon 8–24, execution horizon 1–8, AdamW, LR roughly `1e-4` with logged scheduler, EMA optional. Use a deliberately small validation search. Benchmark latency and closed-loop success; training action-loss alone cannot choose all settings.

**Real intermediate samples:** Add an explicit instrumented sampler that saves `A_{t_k}` at selected scheduler timesteps **before any conversion into world-space trajectories**. Save the encoded condition ID, scheduler coefficients/timestep, noise seed, normalized action tensors and denormalized candidate actions. These are genuine model outputs for the website. Label noisy action sequences as *proposals*; do not display them as a physical path the robot actually traveled. For path overlays, integrate candidate commands through a clearly identified kinematic approximation or short clone simulation and label it accordingly.

## 5.6 Optional advanced architecture: Diffusion Transformer (DiT-style)

A conditional Transformer denoiser over action tokens with diffusion-timestep embeddings and observation cross-attention/FiLM conditioning is a **stretch**, not necessary for the Level 1 release. Implement only after core diffusion is competitive/reproducible and budget approved. Report parameter count, matching training budget and inference latency. No automatic assumption that attention wins against a U-Net on small demonstration datasets. If omitted, document the reason and don't claim a DiT was evaluated.

## 5.7 Architecture parity and counterfactual checks

- Run all families under the same train/val episode IDs, normalization, control horizon, reward and success criteria, simulator version and held-out initial states.
- Track compute budgets and number of hyperparameter trials. A heavily tuned diffusion model compared with an untuned tiny MLP does not establish architectural superiority. At minimum offer a tuned capacity-matched BC baseline.
- Test at least 2 diagnostic ablations after a full core comparison: observation history 1 vs 2+, prediction/execution horizon, diffusion denoising steps, action normalization method, EMA or no EMA, state-proprioception vs privileged object state; **freeze first**.
- Test input perturbation and sensitivity. Check out-of-range observation behavior, no-op action, maximum action clipping, NaN handling and robot joint-limit enforcement in the simulator.

# 7. LEVEL 1 EXPANSIONS AND LEVEL 2 POINT-CLOUD RESEARCH

## 7.1 Secondary 3D manipulation task: Can

After **Lift** models and validation have passed, run **Can** using compatible PH data and environment, identical algorithm families, predeclared model budgets and independent test initial states. Can is a pick-and-place task (grasp a can and put it in a bin), not a generic “place any shape anywhere” benchmark. It involves a different success condition and may require a different controller or action representation; check and configure per task. Do not count saved demonstration frames as rollouts.

An overall headline metric combining Lift and Can is permitted **only if the aggregation rule was frozen before test evaluation**; prefer task-by-task results. If Can proves unavailable or a model fails to learn it despite proper training, report the blocked task or honest zero/low success rather than quietly deleting it.

## 7.2 Level 1 RGB-conditioned policy study

The RGB extension tests whether policies can act from **camera pixels plus robot proprioception**, not from exact object-pose privilege. Once raw simulator snapshots and cameras are reproducibly replayable:

1. Generate **aligned RGB frames** from the exact corresponding demonstration states at 84×84 or 128×128 (choose via throughput/accuracy pilot). Save camera intrinsics/extrinsics, rendering backend, model XML, frame hashes and episode/time indices.
2. Verify image/state alignment by manual visual inspection of a fixed random sample and a code test comparing projected object position with segmentation/visible location where available.
3. Share identical frozen RGB encoder initialization (e.g., a compact ResNet), augmentations, preprocessing, and proprioceptive features across visual BC and visual diffusion. Record whether encoder is trained from scratch, pretrained and frozen, or fine-tuned.
4. Use a **held-out RGB test initial-state suite** and identical simulator/controller/settings. Report visual-only relative to visual-only for architectural claims. State-based Level 1 remains an **oracle-style comparator** when it uses privileged object state.
5. Add view/lighting changes only if the renderer and training inputs make them meaningful; do not claim camera robustness if the model always saw the same camera.
6. If dataset extraction is too expensive or incompatible, publish an honest feasibility note and do not show untrained RGB policy renders as learned visual control.

## 7.3 Level 2 gate: explicit 3D geometry, not just a prettier 3D viewer

**Level 2 only begins once Level 1 core results are finalized and traceable.** Author `docs/LEVEL2_GO_NO_GO.md` containing: (a) precise hypothesis and baseline; (b) approved compute/dataset budget; (c) reproducible depth/point-cloud extraction from corresponding demonstration states; (d) verified camera projection and coordinate frames; (e) comparison protocol; (f) an explicit fallback if it fails. If any component is absent, write `NOT EXECUTED` and continue finishing the project.

Implement a **DP3-inspired** point-cloud-conditioned policy **only if feasible**. Do not claim official DP3 reproduction unless following its actual published implementation/protocol and meeting its constraints.

Possible architecture:

```text
RGB-D camera / simulator depth
    │ calibrated projection, mask, depth units, camera extrinsics
    ▼
3D point cloud XYZ (world or camera frame, explicitly logged)
    │ crop workspace, sample N points reproducibly, optional semantic mask
    ▼
compact point encoder (PointNet-style / published DP3-style encoder)
    │ aggregate features + robot proprioception
    ▼
conditional diffusion U-Net (same policy backbone where practical)
    │ action chunks, identical control/environment as RGB baseline
    ▼
closed-loop 3D manipulation
```

Guard against **ground-truth leakage:** if the visual policy uses object segmentation masks or world-frame coordinates derived from simulator labels, mark this as a privileged-geometry experiment. A valid pure geometric-vision experiment should obtain points from sensor-like depth and calibration alone. Explicit robot segmentation may be treated as a separate, labeled ablation. Do not compare privileged GT object masks to raw RGB and call it a vision-method superiority finding.

**Calibrated depth conversion:** Verify image width/height, perspective versus orthographic projection, near/far plane, depth-buffer normalization and physical units, camera pose to world transform, coordinate handedness, UV convention and invalid/background pixels. Include a numerical test projecting a known 3D simulator point into image pixels and back within tolerance. Show an overlay image that verifies point-cloud alignment with actual robot geometry.

**Experiment:** At minimum match point-cloud diffusion against an RGB diffusion policy with identical demonstrations, robot proprioception, held-out starts, action normalization, horizon, optimizer/training budget and observation sampling rate. Compare in-distribution and precommitted object-placement changes; optionally add camera-pose perturbations with clear distinction between image and world-coordinate point-cloud invariance. Log point-cloud sample size and throughput.

If visual extraction or GPU memory fails, terminate Level 2 without rewriting earlier results. Document what was learned about feasibility, the tests performed and the next technically sound step. Do not require expensive Level 2 to mark the project as complete.

## 7.4 Other stretch experiments, only after main result

- **DiT denoiser** versus U-Net on a single task at comparable capacity/compute.
- **Action mode visualization:** sample multiple diffusion chunks from the *same* fixed condition; quantify spread and show resulting paths in state space, rather than claiming multimodality merely because noise exists.
- **Dataset-quality study:** PH vs properly labeled MH demonstrations on one task, ensuring no model receives more/cleaner data unfairly.
- **More precise assembly:** `Square` is a precision nut insertion task; use it only if the compatible dataset and simulator pass the same Session 0-style contract.
- **ManiSkill StackCube:** independent task and simulator with separate protocol and datasets, no pooled success table with robosuite.

**If RGB/point clouds cannot be derived:** Mark optional extensions as blocked/skipped. Keep the scientifically completed state-conditioned Level 1 comparison and publish it on its merits.
